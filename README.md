## Phase 3 · 長照機構 AMR 車隊協作模擬（Kachaka × 緯創 BestShape VS）

`src/phase3_scene.html` 是一個 Three.js 3D 場景：多台 Kachaka Pro（預設 3 台，可調 1–5 台）在四層樓的長照機構（榮家型態）中分工，執行住民生命徵象巡房、異常複測、藥品配送與失智照顧專區巡視，共用一部電梯與四個充電座，並和護理師、照服員、藥師互動。畫面上下左右的側欄即時顯示車隊狀態、任務佇列與派工理由、量測數值與事件；另有即時平面圖、機器人時間軸、即時數據圖表、導覽模式，以及在背景重跑同一個早上的「策略實驗室」。

### 看點速覽

- **▶ 導覽**（右上）：約 5 分鐘走完一個腳本化的早上——早班派工 → 電梯 → 生理異常與醫囑緊急用藥 → P1 插單與合併 → 電梯尖峰 → 機器人故障與改派 → 電梯停用與恢復 → 數據總覽。每章自動切換視角、平面圖與圖表，章與章之間自動快轉
- **3D／分割／平面**（舞台右上）：平面圖同時顯示四個樓層的機器人、規劃路線、正在使用的房間（以佔用機器人的顏色標示）、等候數、電梯位置與停用狀態、生理異常床位；點機器人可在 3D 跟隨，點樓層名稱可放大
- **時間軸**（下方面板）：每台機器人每一刻的狀態（任務／等待／充電／待命／故障），疊上 P1 插單、異常通報、故障、改派與電梯停用時段，滑鼠移上去看細節
- **即時數據**：各機器人電量走勢（含回充／強制回充／恢復派工門檻）、待派任務與電梯排隊、各機器人時間分配
- **策略實驗室**：車隊規模 1–5 台、四種派工策略、合併派工與 P1 插單開關、有無異常，各在背景完整模擬同一個早上並比較；可用目前設定重跑

### 任務

| 任務 | 優先級 | 內容 |
| ---- | ------ | ---- |
| 生命徵象巡房 | P3 | 對接該樓層量測車，逐床在 1 公尺內量 30 秒心率與呼吸，經 MQTT 寫入護理紀錄；心率 > 110 或呼吸 > 24 推播護理站與 LINE 群組 |
| 異常複測 | P2 | 異常後 10 分鐘（可調）自動建立 |

| 失智專區巡視 | P4 | 2F 四個巡檢點；發現住民往出入口移動時停下來對話並通知照服員 |

任務會依排程自動產生（間隔可調，派單時間與樓層依「情境編號」有日常變化），也可以在下方面板按 ＋配送、＋緊急配送、＋巡房、＋巡視，或從「情境示範」選 電梯尖峰、低電量交接、機器人故障、電梯停用 現場示範。

### 異常情境

- **機器人故障**：下一台行進中的機器人停在原地（模擬前方障礙卡住）、保留所在房間的通行權並通知該樓層人員；20 秒後若車上沒有家具，任務改派其他機器人（保留巡房進度），載著量測車或藥品櫃時則等人員排除後由它繼續；2.5 分鐘後復歸。故障期間不會被派工或被 P1 中斷
- **電梯停用**：電梯系統回報維護（預設 4 分鐘，導覽中為 5 分鐘）。正在搭乘的一趟會完成；新的跨樓層任務在電梯廳等候、同樓層任務照常；派工不會把需要搭電梯的任務交給其他樓層的機器人；恢復後依排程策略消化等候者

### 任務派發策略（可在「調度設定」切換）

1. **佇列排序**：依「有效優先級 → 建立時間」。優先級老化：每等候 N 分鐘升一級（最多到 P2，不與真正的 P1 搶先）
2. **資源檢查**：巡房／複測需要該樓層量測車；配送需要藥品櫃，預設保留最後一櫃給 P1
3. **候選機器人**：閒置、未在低電量充電、電量 ≥ 可派工最低電量，且預估完成任務並回到充電座後仍高於強制回充門檻 5% 以上（充電座上補電中的機器人可直接接單）
4. **挑選方式**
   - 綜合評分：`成本 = 行程時間×w1 + (100−電量)×1.5×w2 + 搭電梯×(40+25×排隊數)×w3`，取最低（權重可調）
   - 最近優先：預估到達時間（含電梯排隊）最短
   - 樓層責任區：交給負責該樓層的機器人，忙碌時可改派最近者
   - 輪流指派：K1→K2→K3… 依序，跳過忙碌或電量不足者
5. **合併派工**：複測併入同樓層進行中的巡房；同樓層配送在備藥前併成一趟（最多 3 份）
6. **P1 插單**：無空閒機器人時，若有機器人即將歸還藥品櫃就等它；否則中斷一台執行 P3／P4 的機器人，在安全點（量完一床、走完一個巡檢點）歸還量測車後接手，原任務保留進度回到佇列，由其他機器人接手

每筆指派的理由與各機器人的分數會顯示在任務卡片與事件記錄（可篩選 派工／交通／充電／照護）。

### 交通管制

- 走廊雙向車道、靠右行駛（東行靠前側、西行靠房間側），同向跟車保持可調中心距，遇人減速禮讓
- 住民房、藥局、機器人站、被服室、護理站取件點為單一通行區：在自己車道、門前約 1 公尺處預約，佔用時就地等候；放行順序可選先到先過或優先級
- 機器人必須先離開原區域回到車道才會等待下一個區域，因此不會形成循環等待；停在充電座的機器人不佔用走道
- 交會時在車道上直行者優先，互相擋住時由優先級高者先行；讓行只看「接下來要走的路線」上的機器人，轉彎之後才會遇到的不算擋路
- 剛出房門又要回同一房間、而房間已被佔用時，不在門口等，而是繞到另一側車道的等候點；若取得通行權的機器人被一台已在門口等同一房間的機器人擋住，會讓出通行權排在它後面，避免互等
- 電梯一次載一台；機器人在電梯廳沿牆的等候點排隊，排程可選先到先服務／任務優先級／最近樓層，等候超過 2 分鐘者優先；電梯會先移到下一個要接的樓層

### 充電管理

- 閒置時低於回充門檻就去充電，充到恢復派工電量前不接新任務；工作中低於強制回充門檻時在安全點交接任務
- 充電座分配：最近可用（含電梯排隊的行程最短）或固定歸屬
- 充電座不足（例如 5 台機器人）時，低電量者先到待命點排隊，已充飽且閒置的機器人會讓出充電座
- 電量變化預設加速 8 倍以便示範（可調）

### 策略實驗室（`lab.js`）

- **同一個早上**：07:58–09:00，例行排程照常，再加上腳本事件 08:06 緊急用藥 4F、08:14 三樓層同時配送、08:22 機器人故障、08:32 電梯停用 5 分鐘、08:44 緊急用藥 3F
- **三個情境**：情境編號（隨機種子）改變派單時間（±45%）、配送樓層、藥師備藥與護理師取件的等待、第二輪巡房偶發的異常數值。隨機數依「用途」取用（例如某床第幾輪、某時刻的訂單），不受派工順序影響，因此不同設定看到的是同一個早上
- **每一格都是完整模擬**：在背景另建一個不顯示的世界，使用同一套派工、交通、電梯、充電與故障邏輯，以 0.05 秒固定步長跑完；畫面上的模擬在重跑期間暫停
- **指標**：緊急用藥送達（醫囑建立到護理站簽收）、平均等候派工（建立到開始執行，09:00 仍在等的以 09:00 計）、完成任務、機器人使用率、等待時間占比、行駛里程、電梯搭乘
- 預設結果在 `labDefaults.js`（由 `npm run lab` 產生，約 30 秒），頁面打開即顯示；「以目前設定快速重跑」（1 個情境，約 15 秒）或「完整重跑」（3 個情境）會用調度設定中的權重、門檻、電梯與充電策略重算

預設設定下 3 個情境的平均（`npm run lab` 輸出）：

| 設定 | 緊急用藥送達 | 平均等候派工 | 完成任務 | 使用率 |
| ---- | ----------- | ----------- | ------- | ----- |
| 1 台・綜合評分 | 7.6 分 | 20.4 分 | 9.0 件 | 72% |
| 2 台・綜合評分 | 6.0 分 | 7.7 分 | 20.0 件 | 75% |
| **3 台・綜合評分** | **4.7 分** | **1.9 分** | **22.7 件** | **63%** |
| 4 台・綜合評分 | 4.7 分 | 1.3 分 | 24.0 件 | 50% |
| 5 台・綜合評分 | 4.7 分 | 1.1 分 | 23.7 件 | 41% |
| 3 台・最近優先 | 4.7 分 | 1.9 分 | 22.0 件 | 63% |
| 3 台・樓層責任區 | 4.5 分 | 2.2 分 | 22.7 件 | 63% |
| 3 台・輪流指派 | 6.3 分 | 3.0 分 | 21.7 件 | 64% |
| 3 台・關閉合併派工 | 5.8 分 | 6.6 分 | 20.0 件 | 66% |
| 2 台・關閉 P1 插單 | 6.8 分 | 7.1 分 | 19.7 件 | 75% |
| 3 台・無故障與電梯停用 | 4.6 分 | 1.7 分 | 23.3 件 | 64% |

讀法：3 台是這個早上的甜蜜點（再加一台只少 0.6 分等候、緊急用藥沒有更快，使用率卻降到 50%）；不看距離的輪流指派讓緊急用藥慢約四成；合併派工對等候時間的影響最大。這些是本模擬的示範結果，不代表實際機構的數據。

### 可重現的模擬

- 設定中的「情境編號」決定當天的隨機性；導覽固定使用情境 1 與上述腳本事件
- `metrics.js` 記錄每台機器人的狀態區段（時間軸）、每 15 秒的佇列／電梯／電量樣本與重要事件，供圖表與實驗室使用
- 畫面上的模擬依每一幀的時間步進，與背景實驗的固定步長略有差異；同一組設定在實驗室中重跑結果完全相同

### 響應式版面

- 寬螢幕：上（模擬時間與 KPI、速度、導覽、調度設定）／左（車隊、選定機器人遙測、LiDAR、電梯排隊）／中（3D、平面圖或分割）／右（量測數值、通報、量測紀錄）／下（任務看板・時間軸・即時數據、即時事件）
- 平板：舞台全寬（分割時 3D 與平面圖並排），面板兩欄並排
- 手機：舞台固定在頂端（3D 或平面圖），依序是車隊、任務與圖表、量測、統計、事件；調度設定改為底部抽屜，策略實驗室全螢幕
- 支援淺色／深色主題與 `prefers-reduced-motion`；設定值存在瀏覽器（無法儲存時仍可使用）
